# Search on MongoDB

Search & Discovery is a read projection over Catalog's and Inventory's events (`catalog.product`, `catalog.category`, `inventory.stock`), kept in its own Mongo database, `search`, which it can rebuild from the compacted topics at any time. Mongo's text index finds the candidates for a search, and one aggregation joins each candidate's Stock to it. Filtering, sorting, paging and facet counting then run over those candidates in application code, in the pure `Search` domain class. Facets are disjunctive: each is counted over the candidates matching every filter but its own, so a Category with five attributes takes nine passes over the same in-memory list (the results, the Category, each attribute, the price and in-stock) rather than nine queries.

v1's requirements are text over a name, a description and attribute values; filters on a Category, attribute values, numeric ranges, Price and Stock; four sorts; and disjunctive facet counts, over a Catalog of tens of Products, growing to a few thousand. Mongo, already in the default stack and the store Reviews & Ratings is planned on, covers each of them: a weighted text index with English stemming and a relevance score for the text, documents shaped like Catalog's events for the rest, and a `$lookup` for the Stock. Nothing in v1 needs fuzzy matching, typo tolerance, synonyms, autocomplete or per-language analysis. Those are what a search engine is for.

## Considered Options

- **A search engine (OpenSearch or Elasticsearch).** Rejected for v1. It brings typo tolerance, synonyms and aggregations built for facets, but it is another stateful cluster to run, size and secure, and a JVM that alone outweighs Search's memory cap. No v1 requirement needs what it adds beyond Mongo.
- **Filter and count in Mongo, with `$facet`.** Rejected for v1. One `$facet` stage can count every facet in the database, but each disjunctive facet needs its own sub-pipeline that repeats every other filter. The matching rules would then be written twice, as Mongo criteria for the results and again for each facet, or else generated, and the pure domain test could no longer cover the counting. At v1's size, counting a few thousand small documents in memory takes milliseconds.
- **Query Catalog and Inventory directly.** Rejected because Catalog's Couchbase indexes serve key and Category reads, not text, and asking Inventory for every listed Variant's Stock on each search would tie the listing to Inventory being up. A projection also keeps search load off both.
- **Denormalize Stock onto each Product document.** Rejected because a Stock event would then have to find and rewrite its Product, which may not have arrived yet; a Variant's Stock may come before its Product, or the other way round. Keeping Stock in its own collection, keyed by Variant ID, and joining it at query time makes either order work.

## Consequences

- Every search loads every candidate the text matched, or every Product when there is no text, with its Stock. That costs memory and time in proportion to the Catalog. Once a search reads more than about 10,000 Products, or its p95 latency passes 200 ms, move the filters into the Mongo query and the facets into `$facet`. If Customers need typo tolerance or synonyms by then, move to a search engine instead. The [roadmap](../../../../docs/roadmap.md#sprint-9-weeks-1718--search-engine--event-contracts) moves Search to Elasticsearch in Sprint 9. The `Search` domain test pins the counting rules either move has to keep.
- Text search is Mongo's: whole words, stemmed in English, any of the words matching, ranked by a score weighted toward the name. A misspelling finds nothing, and there are no partial words or prefixes.
- Mongo runs as a single node with no replica set, so it offers no multi-document transactions. The projection doesn't need them: one aggregate's events arrive in order on one partition, and applying one reads and writes a single document.
- The projection keeps removed Products and Categories, marked as removed, so a stale event can't bring one back. They stay until a rebuild.
- "Newest" orders Products by when Search saw them listed, since Catalog's events don't say when a Product was created. A rebuild replays only each Product's latest event, so after one, every Product counts as listed when it last changed.
