# Sprint Roadmap

Nine two-week sprints, five tracks running in parallel for a 4-5 person team. Sprint 1 is a deliberately thin **walking skeleton** through every layer — the fastest way to retire integration risk before any track goes deep.

## Tracks

| Track | Mandate | Owns |
|---|---|---|
| **A — Platform & Identity** | Infra, auth, and the shared plumbing every other track depends on | Identity & Access, Notifications, CI/CD, API Gateway, Observability |
| **B — Catalog & Discovery** | What customers find and trust before they buy | Catalog, Search & Discovery, Reviews & Ratings, Recommendations |
| **C — Cart, Checkout & Payment** | Turns browsing into a paid, priced order | Cart, Checkout & Pricing, Promotions, Payment |
| **D — Order, Fulfillment & Returns** | Owns an order's truth from placement to delivery — or its return | Order Management, Inventory, Fulfillment & Shipping, Returns & Warranty |
| **E — Frontend & AI Assistant** | Where customers touch the system, human or AI | Storefront, Admin Console, Support Assistant |

## Sprint 1 (Weeks 1–2) — Walking Skeleton

| Track | Delivers |
|---|---|
| A | Monorepo + Docker Compose (Postgres/Redis/Kafka/Couchbase/Mongo); hexagonal-architecture Spring Boot starter template; minimal JWT auth |
| B | Catalog CRUD + seed data (~20 SKUs, 3 categories); product list/detail read API |
| C | Redis-backed cart; checkout stub; mock payment adapter (always succeeds) |
| D | Order create/status (plain CRUD, no events yet); Inventory as a simple stock counter |
| E | React storefront — browse, cart, checkout, order confirmation |

**Definition of done**: `docker-compose up` → browse seeded products → add to cart → check out with a mock payment → see an order confirmation and status — entirely local.

> **Note (Sprint 1 implementation):** Kafka and Mongo are defined in Compose but sit behind the `full` profile (`docker compose --profile full up`), because nothing uses them until Sprint 3 and the default stack has to fit in about 8 GB of Docker memory. A plain `docker compose up` (or `make up`) starts everything the definition of done needs, with the [Storefront](../frontend/storefront/README.md) on http://localhost:8080. The root README's run section walked through it, and a Playwright smoke test proved it; [Run Sprint 4](../README.md#run-sprint-4) has since taken its place, Sprint 1's path included.

## Sprint 2 (Weeks 3–4) — Harden the Skeleton

| Track | Delivers |
|---|---|
| A | CI pipeline (build/test/lint/containerize); structured logging + correlation IDs; API gateway auth enforcement |
| B | Product variants + category attributes; admin catalog CRUD API |
| C | Pluggable payment-gateway interface; first promotion rules; checkout price calculation |
| D | Inventory reservation semantics (reserve on checkout, release on timeout) |
| E | Admin console shell (staff login, catalog editor); storefront polish + error states |

> **Note (Sprint 2 implementation):** The definition of done holds after `make up`: CI is green on `main`; a Customer picks a multi-Variant Product, opens checkout and sees their Checkout Session held for 15 minutes, applies `WELCOME10`, is declined once and then pays for a `PAID` Order with its Discount; Staff create a Product with two Variants and Stock in the Admin Console, and the Storefront shows it; an abandoned Checkout Session gives its Stock back once its Reservation expires; and one request can be followed across services in the logs by its Correlation ID. The root README's run section walked through it; [Run Sprint 4](../README.md#run-sprint-4) has since taken its place. The Storefront's and the Admin Console's Playwright suites prove the Customer's and the Staff's paths in CI; the expiry and the Correlation ID were shown by hand.
>
> What the build settled on:
>
> - **Stock is held, not taken, at checkout.** Starting checkout opens a Checkout Session in Redis that holds the Cart's Stock through an Inventory Reservation for 15 minutes; the Reservation lasts 2 minutes longer, so a payment started just before expiry can still commit it. An expired Reservation stops holding Stock at once, and a sweeper marks it released every 30 seconds ([Checkout ADR 0001](../services/checkout-pricing/docs/adr/0001-checkout-sessions-hold-stock-through-reservations.md)). Reservations keep no ledger of Stock movements yet; that is Sprint 3.
> - **Checkout calls the other contexts directly**, as in Sprint 1, now carrying the Correlation ID; the checkout Saga comes in Sprint 4. A declined or failed payment cancels the Order it placed but keeps the session, so the Customer can pay again.
> - **The first promotion rules are Coupons** in a new Promotions service: a percentage or a fixed amount off, with a validity window and an optional minimum. Campaign rules are Sprint 3's.
> - **The payment gateway is a port** with a mock adapter, driven by test tokens that approve, decline, decline for insufficient funds, or fail to answer.
> - **The API gateway** (port 8000) routes `/api/<service>/`, rejects missing or invalid tokens and hides internal endpoints ([ADR 0010](./adr/0010-api-gateway-authenticates-at-the-edge.md)); each service still authorizes every request itself. Rate limiting and circuit breakers wait for Sprint 7.
> - **Logs are JSON** (ECS) under the `docker` profile, each line carrying its Correlation ID. Metrics, tracing and dashboards wait for Sprint 4.
> - **Memory:** the gateway, Promotions and the Admin Console join the default stack, which still fits in about 8 GB of Docker memory with the Sprint 1 caps: `docker stats` measured about 3.4 GB in use on 2026-10-02, with the eight Spring services at 180–250 MB each, Keycloak near its 512 MB cap and Couchbase at 1 GB, so no cap needed lowering.
> - **Existing stacks** need `make seed-reset` once, and the Keycloak realm brought up to date for the Admin Console's sign-in ([A stack from Sprint 3](../README.md#a-stack-from-sprint-3) keeps these steps for a stack from Sprint 1).

## Sprint 3 (Weeks 5–6) — Events & Order History

No context is event-sourced: contexts keep append-only histories and ledgers where a requirement calls for them, and publish state-carrying, versioned integration events through transactional outboxes ([ADR 0002](./adr/0002-ledgers-and-outboxes-not-event-sourcing.md)).

| Track | Delivers |
|---|---|
| A | Kafka topics, partitions & consumer-group design; shared integration-event schemas (JSON Schema in the repo, registered in Apicurio); outbox publishing through Spring Modulith |
| B | Search & Discovery v1 (faceted browse); Reviews & Ratings (post-purchase) |
| C | Campaign rules engine; checkout applies promotions |
| D | Order Management: Order Status history, Order events through the outbox, order-summary read model, history backfilled for existing Orders; Inventory: ledger of Stock movements, Stock events through the outbox |
| E | Order history/detail pages on the new read model, with the real Order Status timeline; admin order list/detail |

> **Note (Sprint 3 implementation):** The definition of done holds after `make up`, on a fresh stack and on one carried over from Sprint 2. The root README's run section walked through it; [Run Sprint 4](../README.md#run-sprint-4) has since taken its place. The Playwright suites prove the Customer's and the Staff's paths in CI. A Customer filters Audio by an attribute and to what is in stock, with the counts changing, and searches. They check out with Audio week applied by itself and `WELCOME10` on top, pay, see Placed then Paid with their times, review the Product and see its Rating summary on its card and page. A Customer who never bought a Product is told they can't review it. Staff find a Customer's Order and its history, see a changed Price in search within seconds, and create a Campaign that the next checkout applies, then find the Order it gave. Some checks were done by hand on 2026-10-06:
>
> - On a Sprint 2 stack, three Orders (one with `WELCOME10`, one declined) and an unpaid Checkout Session, upgraded with `make up` alone, came up with backfilled histories and the Coupon's Discount in the new list. The held laptop's ledger had an opening balance and its Reservation, and it balanced. Search held all 20 Products, and Reviews let the demo Customer review what they had paid for.
> - A Price changed with a Correlation ID showed in search 1.1 seconds later. The ID appeared at the gateway, then in Search's and Reviews' consumers as they applied the `catalog.product` event.
> - A payment made through the Storefront with a Correlation ID was followed from the Storefront's nginx, through the gateway, Checkout and the contexts it calls, into Reviews' consumer applying the Order's events and Search's applying the Stock event.
> - A schema change that isn't backward compatible failing CI was proven with the event backbone (#41).
>
> What the build settled on:
>
> - **Events are snapshots on compacted topics.** Each of `order-management.order`, `inventory.stock`, `catalog.product` and `catalog.category` carries one event type: its aggregate's state, version and why it was published. Topics have 6 partitions locally, and the broker never creates one itself. Their JSON Schemas live in [`platform/event-schemas`](../platform/event-schemas/README.md) and are registered in Apicurio 3.3 with BACKWARD compatibility. Producers validate against them, and consumers read tolerantly.
> - **Publishing goes through an outbox.** The Postgres services use Spring Modulith 2.1's event publication registry, which ran under Boot 4's Jackson 3 beside Apicurio's Jackson 2 serializer, as the spike had to prove. Catalog writes its own outbox document in the same Couchbase transaction, and a relay sends it. Consumers keep the newest version, and they retry an event that fails, then log it and skip it. Dead-letter topics are Sprint 4's.
> - **Histories and ledgers, not event sourcing.** Order Management appends an Order Status history entry with every change, and Inventory a Stock movement with every change to On-hand or to what Reservations hold. Both were backfilled by migrations, and each context publishes everything once on its first start, so projections start complete. The Staff Order list is a query over Order Management's own tables.
> - **Search and Reviews are projections in Mongo.** Search computes disjunctive Facets with Mongo's text index and aggregations ([Search ADR 0001](../services/search-discovery/docs/adr/0001-search-on-mongodb.md)); Elasticsearch is Sprint 9's. Reviews checks a purchase against its own projection of Orders and Products, only when a review is posted ([Reviews ADR 0001](../services/reviews-ratings/docs/adr/0001-reviews-on-mongodb.md)). `make search-rebuild` and `make reviews-rebuild` replay their topics.
> - **Campaigns and Coupons are worked out together.** Promotions returns every Discount a Checkout Session's lines are due, Campaigns by priority and then the Coupon. The session and its Order keep them as a list. Usage limits are Sprint 6's.
> - **Checkout still calls the other contexts directly.** The Saga, idempotency keys and the Orchestration identity are Sprint 4's.
> - **The smoke tests make their own Customers** through Keycloak's admin API, so a review or a Cart is the test's alone. Within the Storefront's suite, every test that checks out sits in the one serial smoke test, since its first test compares Stock before and after; the Admin Console's suite checks out too, so the two run one after the other, as CI runs them.
> - **Memory:** Kafka, Mongo, Apicurio, Search & Discovery and Reviews & Ratings joined the default stack. On 2026-10-06, after both Playwright suites had run, `docker stats` measured about 4.8 GB in use. The ten Spring services were at 200–340 MB each, Catalog nearest its 384 MB cap at 342 MB. Couchbase was at 0.9 GB, Kafka at 350 MB and Mongo at 110 MB. Keycloak's cap went up from 512 MB to 768 MB, with its heap share cut from 60% to 40% so the heap stays about 300 MB. At 512 MB it sat at the limit from start, and after a day of e2e runs it was killed for memory; under the suites it now reaches about 590 MB. The capped containers add up to 6 GB, so the stack still fits in about 8 GB.
> - **Existing stacks** need only `make up`. The root README's section on them now starts from Sprint 3 ([A stack from Sprint 3](../README.md#a-stack-from-sprint-3)).

## Sprint 4 (Weeks 7–8) — Checkout Saga & Payment Ledger

| Track | Delivers |
|---|---|
| A | Temporal server in Compose (Postgres persistence); Orchestration service and its client-credentials identity; idempotency keys on command APIs; retrying event consumers; dead-letter topic handling; consumer-lag & error-rate dashboards |
| B | Recommendations v1 (co-occurrence from Order events) |
| C | Checkout Saga on Temporal ([ADR 0009](./adr/0009-sagas-on-temporal.md)), closing the authorized-but-cancelled gap with a void; Payment rebuilt on a ledger of Payment transactions, with void; idempotent gateway-webhook handling |
| D | Saga-facing commands on Order Management and Inventory; Redis-backed hot stock cache for checkout |
| E | Storefront/admin reflect real payment + stock states |

> **Note (Sprint 4 implementation):** The definition of done holds after `make up`, on a fresh stack and on one carried over from Sprint 3. The root README's [Run Sprint 4](../README.md#run-sprint-4) walks through it. The Playwright suites prove the Customer's and the Staff's paths in CI. A Customer pays with `tok_approve` and sees the Order paid with its authorized Payment. They pay with `tok_async_approve`, see "Confirming your payment…", then the paid Order, its Payment approved by the gateway's webhook. They pay with `tok_async_decline`, are told why, and pay the same session with `tok_approve`. After buying two Products together, they see each under "Customers also bought" on the other's page. Staff open a paid Order and see its Payment's transactions, and set a Variant's Stock and see its movements, balanced. Some checks were done by hand on 2026-10-12, on a stack built from `fde7140`:
>
> - **A hold that lapses during a pending authorization.** The demo Customer paid with `tok_async_approve`. Once the Payment was `PENDING`, the Reservation was made to lapse by setting its `expires_at` to the present in Inventory's database, rather than waiting 17 minutes as on 2026-10-09 (#61). The webhook approved the authorization 3 seconds after it was made; the commit answered 409; the Payment was voided 2 seconds later and the Order cancelled, both by `ORCHESTRATION`. Pay answered 410 `holdExpired` ("nothing was charged"), and the attempt read `HOLD_EXPIRED`. The Payment shows the pending authorization, the webhook's approval with its event ID, and the void.
> - **Order Management stopped mid-checkout.** With Order Management stopped by `docker stop`, a Pay answered 202. Started again 2 seconds later, it was healthy 13 seconds after it stopped, and the attempt read `PAID` 4 seconds after that. Temporal's history shows placement started on its 5th attempt, carrying the previous attempt's failure (Order Management's address not resolving), and every later step on its first. Placement is retried for about a minute: started with `docker compose start` instead, which reruns the one-shot init steps it depends on first, Order Management took 85 seconds to come back, and two attempts ended `FAILED` with nothing to undo, as #60 found.
> - **Dead-lettering and redrive.** A malformed `inventory.stock` event, under a key of its own so that compaction keeps every Variant's last event, was on `search-discovery.stock.dlt` within seconds, with no retries. With Mongo stopped, Staff set Pixel 9's On-hand to 26; Search dead-lettered the Stock event after its retries, 3 minutes 16 seconds later. With Mongo started again, `make dlt-redrive GROUP=search-discovery.stock` redrove 3 events in under 6 seconds: Search applied the Stock event (version 748, 26 available), logging its Correlation ID, and the two malformed events, this one and the one left by #62, went back to the dead-letter topic.
> - **Grafana's dashboards** showed the run. **Checkout Saga:** 13 checkouts `PAID` in 90 minutes, with other outcomes beside them; 7 `placeOrder` step failures; Temporal's activity failures and workflow durations. Its panels plot `increase()` of Orchestration's counters, which misses a counter's first increment, as #62 found for dead-lettered events: the lapsed hold's void, the first since Orchestration started, never showed under Compensations, and only 3 of the 4 outcomes showed. (Later, in #69, Orchestration came to register every outcome, step and compensation at 0 when it starts, so each first count shows.) **Event consumers:** consumption per group and topic, retries, 4 dead-lettered events and 1 redriven. **Services:** request and 5xx rates, p95 latency, the outbox gauge and a Stock cache hit ratio of 94%. **Consumer lag stayed at 0**, even while Search's Stock partition was blocked: the panels plot the Kafka client's `records-lag`, which counts from what a consumer has fetched, so an event held in retries, or a stopped consumer, which reports nothing, doesn't show. On these topics, a few hundred events each, `make search-rebuild` catches up between two scrapes. Lag that counts from the committed offsets needs the broker's view, such as a Kafka exporter's. (Later, in #68, a Kafka exporter joined the stack, and the lag panels came to read the lag of each group's committed offsets. With Search & Discovery stopped, three Stock changes put `search-discovery.stock` at 1, 2 and 3; with Mongo stopped, it read 1 from the next scrape until the event was dead-lettered 3 minutes later. A partition a group has never committed on, which the exporter reports as -1, counts every event it holds.)
> - **Upgrading a Sprint 3 stack.** Following [the upgrade check](./agents/upgrade-check.md) from `e40cbc0`, the demo Customer placed a Paid Order with Audio week and `WELCOME10`, a declined then Paid one from one session, and a Paid Order of an XPS 13 with Sony headphones, and left a Checkout Session unpaid. `make upgrade-to` took 4 minutes 39 seconds and came up healthy; this tree's images had been built beforehand, beside the Sprint 3 stack, since building them all takes about half an hour and the session had to be paid within its 15 minutes. The realm gained the `ORCHESTRATION` role and the `orchestration` client. The 4 Payments became one backfilled `AUTHORIZATION` each, 3 approved and 1 declined with `card_declined`, and `payment.payment` held each once as `BACKFILLED`. The unpaid session, started 5 minutes before the upgrade, was paid through the Saga, its Order's history showing `ORCHESTRATION` where the Sprint 3 Orders' show `CHECKOUT`. Recommendations had each of the laptop and the headphones as the other's "Customers also bought". Search listed all 20 Products, and every touched Variant's Stock movements balanced. Both Playwright suites passed against it, one after the other. First, its Keycloak's master realm had to be set to `sslRequired: NONE` by hand: a fresh Keycloak keeps the default, `external`, and on this machine host requests reach containers from a public address, so the suites' admin tokens were refused; CI doesn't see this. The first Storefront run also timed out starting a Checkout Session, which took 51 seconds: after an hour idle with Docker's swap full, Cart and Promotions took 9 and 35 seconds to answer their first calls. Run again, warm, it passed.
> - **Memory.** After both suites, `docker stats` measured about 6.2 GB in use, up from 5.4 GB at #57. Catalog was at 375 MB, Checkout at 356 MB and Orchestration at 348 MB of their 384 MB, so no cap could be lowered. Kafka was killed at its own 512 MB cap with no build running (the kernel's log shows a memory-cgroup kill, not a VM-wide one): the broker now takes about 400 MB with this sprint's dead-letter and redrive topics, and each healthcheck starts a JVM of about 100 MB beside it. Its cap went up to 640 MB. The capped containers add up to 7.8 GB, with Couchbase (760 MB), Postgres and Redis uncapped. The stack still runs in 8 GB, though it uses some swap. Rebuilding images beside the running stack takes about 1.3 GB more, and twice ran Docker out of memory: the kernel killed Kafka and Keycloak, and `make status` blamed their caps, since Docker doesn't say which limit was reached. The README says to `make down` first. (Later, in #68, the Kafka exporter joined the stack, capped at 32 MB. On 2026-10-13, after both suites, it used 16 MB, the stack about 5.7 GB, and the caps added up to 7.8 GB.)
>
> What the build settled on:
>
> - **Temporal and Orchestration (#55).** Temporal's server 1.32 joins the default stack, persisting to the shared Postgres in its own `temporal` and `temporal_visibility` databases. An `admin-tools` step sets up or migrates their schema, and another creates the `default` namespace with a 7-day retention. Its UI is on port 8233. Orchestration is its worker on the `checkout` task queue, with a placeholder workflow for now. A spike proved the Temporal Java SDK 1.40 and its Spring Boot starter under Boot 4.1: workflow payloads go through the SDK's Jackson 2 beside Boot's Jackson 3, as Apicurio's serializer does. Each of Temporal's four services keeps its own pools on Postgres, which at their defaults used up the 100 connections it allowed. Their pools were cut, and Postgres now allows 200; idle, the stack holds about 80. Apicurio now restarts with Postgres, since recreating Postgres for that setting cut its pooled connections just as `schema-registry-init` used them.
> - **Idempotency keys (#56).** A Postgres service declares a command idempotent with `@IdempotentCommand`, and `service-commons` does the rest: the command runs in a transaction its use case joins, with the key claimed first and the 2xx response recorded before the commit, so a repeat is replayed and a concurrent one waits for the first. Keys are scoped to the token's `client_id`, or else its `sub`, kept for 7 days and pruned daily. Each service adds the `idempotency_key` table in its own migration, as the [service template](../platform/service-template/README.md#idempotent-commands) shows. The key Orchestration is to send gained the run ID ([ADR 0009](./adr/0009-sagas-on-temporal.md)).
> - **Metrics and dashboards (#57).** `service-commons` brings Micrometer's Prometheus registry, so every Spring service, the gateway included, serves `/actuator/prometheus`, open without a token and tagged with the service's name; the gateway routes no service's `/actuator/**`. Beside Spring's HTTP metrics, with histograms for p95, every service exports Kafka's consumer client metrics, a counter of retried events per group and topic, and, with an outbox, a gauge of its incomplete publications per status. Kafka's client metrics name only the client, so `service-commons` binds them with the consumer group as a tag: added by a `MeterFilter`, the tag broke Micrometer's Kafka binder, which compares tags to tell its meters apart and then bound only the first partition's lag. Kafka also reports per-topic metrics a second time under the topic's legacy name, dots turned to underscores; those copies are dropped. Prometheus 3.15 (2-day retention) and Grafana 13.2 join the default stack on ports 9090 and 3000, Grafana open for viewing, with its data source and the **Services** and **Event consumers** dashboards provisioned from `infra/docker/grafana`.
> - **Memory (#57):** On 2026-10-08, after the Storefront's smoke suite had checked out, `docker stats` measured about 5.4 GB in use, up from 5.0 GB. Prometheus took 67 MB of its 256 MB. Grafana took 229 MB of its 256 MB, of which 107 MB was reclaimable file cache; it runs its schema migrations afresh on every start, since it keeps no volume. The capped containers now add up to 7.3 GB, so the stack still fits in about 8 GB. No cap was lowered, and Prometheus and Grafana stay in the default stack, not behind a Compose profile.
> - **Payment's ledger (#58).** A Payment is now its Payment transactions, `AUTHORIZATION` and `VOID`, which the database refuses to change or delete, and its status (`PENDING`, `AUTHORIZED`, `DECLINED` or `VOIDED`) is worked out from them by one pure function, written beside them in the same transaction. `POST /payments` requires an `Idempotency-Key` and passes it to the gateway, whose mock answers a repeated key with its first answer; Checkout sends `checkout:<orderId>:authorize`. `POST /payments/{id}/void` releases an authorization. Each change publishes a `payment.payment` event, and the gateway now routes the Customer's and Staff's reads. A migration turns each Sprint 3 Payment into one backfilled authorization, and the service publishes each once as `BACKFILLED` when it starts.
> - **Saga-facing commands (#59).** Orchestration's `ORCHESTRATION` token may now place Orders and change their status, authorize, void and read Payments, and commit Reservations, and two new internal commands are its alone: Cart's `POST /carts/clear` and Checkout's `POST /checkout/sessions/{id}/end`, which ends a session only while the Customer's pointer still names it. Each names the Customer as `customerId`, and the gateway hides the commands. Order Management's two commands require an `Idempotency-Key` from Orchestration and record `changedBy: ORCHESTRATION`. This is the expand step: `CHECKOUT` keeps its access, and sends no key to Order Management, through `@IdempotentCommand(exemptRoles = "CHECKOUT")`, until #60 moves Checkout onto the Saga.
> - **The checkout Saga (#60).** Paying a Checkout Session starts Orchestration's `checkout` workflow through Checkout's `CheckoutSaga` port, with the session's ID as the workflow's and the session, Payment method and Correlation ID as its input. Checkout no longer calls Order Management or Payment, nor commits Reservations, and its compensation code is gone. It waits about 10 seconds: 200 when paid, 402 when declined, 410 `holdExpired` when the Reservation had lapsed (the Payment voided and the Order cancelled), 502 when the Saga failed, and 202 while it runs, after which `GET /checkout/sessions/{id}/payment` reports the latest attempt. Temporal being unreachable is a 503 `checkoutUnavailable` within 5 seconds, not Temporal's default minute. The workflow reports `PAID` from its memo once the Order is marked paid, while it still clears the Cart and ends the session. The Storefront shows "Confirming your payment…" on a 202, polls every 1.5 seconds for up to 2 minutes, and resumes after a reload. `CHECKOUT` lost the commands the Saga took over, and `@IdempotentCommand(exemptRoles)` went with it. Inventory's Reservation endpoints check their roles per endpoint: a class-level `CHECKOUT` guarded the exception handlers too, so a 404 or 409 for Orchestration's commit came back as a 500. An activity's failure now carries only its message, since the HTTP client's stacks went past Temporal's size limit and its UI showed "Failure exceeds size limit" instead of why a step was retried. Grafana gains the **Checkout Saga** dashboard.
> - **Checked by hand (#60), on 2026-10-09:** with Order Management stopped, a Pay answered 202. Started again 2 seconds later, Order Management was healthy 51 seconds after it stopped, and the Order was paid 63 seconds after, placement having taken 9 attempts, each with its reason in Temporal's history. Placement is retried for about a minute, so Order Management has to be back within it: once it took longer and the attempt ended `FAILED`, with nothing to undo. Warm, a decline or an approval answers in about a second. The first checkout after `make up` took about 12 seconds and answered 202, while the services warmed up.
> - **Bank-confirmed payments (#61).** The mock gateway answers `tok_async_approve` and `tok_async_decline` with `PENDING`, then about 3 seconds later sends a Gateway webhook settling the authorization as approved, or declined with `card_declined`. Payment's `POST /webhooks/gateway` is authenticated by an HMAC-SHA256 signature of the body, with `PAYMENT_WEBHOOK_SECRET`; the API gateway routes it without a token. Each event ID is recorded once, and a webhook for a Payment already settled or voided is recorded and changes nothing. The mock hands its webhooks to a `WebhookDelivery` port, which tests replace to deliver, repeat, reorder or withhold them. The Saga awaits a pending authorization by reading the Payment, backing off from 1 to 5 seconds, for `ecomm.orchestration.settlement-deadline` (10 minutes); still pending then voids the Payment and cancels the Order, `FAILED`. With a 3-second webhook an async card usually answers inside Checkout's 10-second wait, as a 200 rather than a 202, so the Storefront shows "Confirming your payment…" for any Pay unanswered after 2 seconds.
> - **Checked by hand (#61), on 2026-10-09:** a hold that lapses during a pending authorization. Payment and Orchestration ran with the mock's webhook delay at 18 minutes and the settlement deadline at 20, so the Reservation (held 17 minutes) lapsed first. The demo Customer paid with `tok_async_approve` at 18:47:35 UTC and got a 202. The Saga read the Payment as pending every 5 seconds; the Reservation lapsed at 19:04:35; the webhook approved it at 19:05:38; the commit answered 409, the Payment was voided at 19:05:40 and the Order cancelled. The attempt ended `HOLD_EXPIRED`, and the Payment shows its pending authorization, the webhook's approval with its event ID, and the void.
> - **Dead-letter topics (#62).** A listener's failure is retried 5 times, after 0.5 to 8 seconds, blocking its partition. The event then goes to its consumer group's dead-letter topic, `<group>.dlt`, with Spring Kafka's `kafka_dlt-*` headers naming its original topic, partition, offset and group and the error's innermost cause, and `ecomm_dlt-dead-lettered-at`. The error-level log line stays, and the partition moves on. An event that can't be read, malformed JSON or missing a field its listener marks `@JsonProperty(required = true)`, goes there at once; Search's and Reviews' listeners mark the fields they dereference, all of them required by the schemas. `make dlt-redrive GROUP=<group>` copies the group's dead events since the last redrive to `<group>.redrive`, which every `@KafkaListener` that names its topics and group also consumes, through an annotation enhancer in `service-commons`, so a redriven event is applied by version and one that fails again is dead-lettered again. The copy runs as a plain Java main from `service-commons`, in the service's own image, since Kafka's image has no compiler and its console tools can't copy binary headers. The topics init creates both topics for every group in `infra/docker/consumer-groups`, which the Makefile reads too: 6 partitions, not compacted, kept 14 days. **Event consumers** gains dead-lettered and redriven events, plotted as counters since each service started, since a rate misses a counter's first increment. The retries counter no longer counts a failure that isn't retried.
> - **The Stock cache (#63).** Inventory keeps one entry per Variant in the stack's Redis, `inventory:stock:<Variant ID>`, with its On-hand, what Reservations hold, available, whether it is stocked and its Stock version. Every change writes it once its transaction commits, a Lua compare on the version keeping a late write from overwriting a newer one, and a miss fills it from Postgres. An entry lives for the earlier of 60 seconds and the soonest `expiresAt` of the Reservations holding the Variant, so Stock an expiring Reservation gives back is available at once. `GET /stock/{variantId}` and a new public batch read, `GET /stock?variantIds=…` (1 to 50), are served from it, and a Reservation it already shows can't be met is a 409 `insufficientStock` without a Postgres transaction. With Redis down, reads and Reservations go to Postgres, each failed call logged at warn and counted; Redis doesn't count in Inventory's health. The Services dashboard shows the hit ratio, hits, misses and errors. > What the build settled on:
>
> - **Refunds (#84).** `POST /payments/{id}/refunds`, Orchestration's alone with an `Idempotency-Key`, records a `REFUND` Payment transaction naming what it is for, such as an RMA reference. The Payment goes `PARTIALLY_REFUNDED`, then `REFUNDED` once the Refunds reach the amount captured; more than is left, or another Currency, is a 422 `refundExceedsCaptured`, a Payment not captured a 409 `paymentNotRefundable`, and a declined Refund a 402 recorded with its reason (`tok_refund_decline`).
> - **Restocks and replacement Reservations (#85).** `POST /stock/{variantId}/restocks` records a `RESTOCKED` movement with the RMA reference, once per reference. Orchestration reserves for an RMA as `rma:<rmaId>`, one Reservation not yet released per RMA.
> - **Replacement Shipments and return addresses (#86).** A Shipment is `ORDER` or `REPLACEMENT`, one of each per Order or RMA; a replacement is picked, packed with new Serial numbers, dispatched and delivered like any other, and nothing captures a Payment for it. `?rmaId=` reads it. Each Warehouse has a return address, which a Customer may read.
> - **The RMA lifecycle (#87).** `APPROVED → RECEIVED | EXPIRED`, `RECEIVED → INSPECTED`, `INSPECTED → REFUNDED | EXCHANGED | CLOSED | ON_HOLD`; any other step is a 409 `transitionRefused`. An approval sets the Send-back deadline, the later of the window's end and 14 days after it, and the Warehouse. Each RMA's Refund amount is its units' Prices less their share of the Discounts plus their share of the Tax, by largest remainder, so RMAs covering every unit come to the total less Shipping, from a projection of `order-management.order`.
> - **The returns Saga (#88).** An `APPROVED` RMA starts `returns:<rmaId>`, which awaits the units until `sendBackBy` on a durable timer and expires the RMA then, awaits its Inspection with an hourly re-read, and restocks and refunds an accepted return, reserves and ships a replacement for a confirmed fault (refunding instead when there is no Stock), or closes a refused one; a declined Refund holds the RMA. When an RMA's Refunds cover its Order's units, the Order goes `RETURNED`. Grafana's Sagas dashboard has a Returns row.
> - **The Admin Console's RMA lifecycle (#89)** and **the Storefront's returns (#90).** A tab per stage, Serial numbers checked as Staff type them on receipt, and the outcomes for the RMA's kind on inspection; a Customer requests from a delivered Order's page, choosing units by Serial number, and follows each RMA under **My returns**, with its Return address and Send-back deadline once approved.
> - **Notifications (#91–#93).** A new service on port 8101, with a `NotificationProvider` per channel: email over SMTP to Mailpit in the compose stack, and mock SMS and push providers that record what they would send. It consumes `order-management.order`, `fulfillment-shipping.shipment`, `payment.payment` and `returns-warranty.rma`, each group from the latest offset on its first start, records one Notification per event, channel and Customer in the Notification ledger, and a dispatcher sends and retries them. Each Message type names its channels and has templates only for them: the Order confirmation and the RMA messages go by email alone, shipping, delivery, replacement and Refund messages by email and, as a Customer chooses in their Notification preferences, SMS and push. The Customer's address comes from Keycloak through the `notifications` client's service account.
> - **Coupon usage limits (#94).** A Coupon may have a Usage limit and a limit per Customer; existing Coupons have neither. Applying one at checkout holds a use for the Checkout Session until it expires, so a used-up Coupon is refused at once as `exhausted` or `alreadyRedeemed`; the checkout Saga redeems it once the Order is paid, behind `Workflow.getVersion("coupon-redemption")`, and paying honours a Coupon that ended meanwhile. A redemption is never given back.
> - **Abandoned Carts (#95).** A Cart that holds Variants and is unchanged for 24 hours is published once per abandonment as a `cart.cart` `ABANDONED` event, by a sweep every 5 minutes under a Redis lock, with Kafka's idempotent producer and no outbox ([ADR 0002](./adr/0002-ledgers-and-outboxes-not-event-sourcing.md)'s dated note); `cart_abandoned_total` counts them.
> - **Review moderation (#96).** A review is `PUBLISHED`, `HELD` or `REMOVED`. A screened word, matched as a whole word whatever its case or accents, holds it; Customers report others' reviews; Staff publish, dismiss the reports or remove one with a reason. Only published reviews are listed and counted.
> - **Recommendations' quality pass (#97).** Out-of-Stock Products are left out, only Orders from the last 180 days count, and fewer than the limit bought together are filled with the Category's best sellers, each with its reason.
